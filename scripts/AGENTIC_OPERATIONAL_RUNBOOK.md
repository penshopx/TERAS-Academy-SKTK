# Runbook operasional Agentic TERAS — trainer intelligence

**Pemilik:** operator admin (pemantauan), engineering/on-call (investigasi teknis), governance (keputusan rollout dan baseline). **Berlaku untuk:** agent `trainer-intelligence`, bukan pemeriksaan keputusan kompetensi/sertifikasi. Gunakan waktu UTC dan hanya agregat aman. SOP ini tidak memberi izin membuka data learner untuk investigasi agent.

## Sumber dan batas pencatatan

- Di TERAS Academy, masuk sebagai admin ke **Kondisi platform → Kesehatan analisis AI** (`artifacts/teras-academy/src/pages/admin.tsx`; sumber `GET /api/admin/agent-observability` di `artifacts/api-server/src/routes/admin.ts`). Catat waktu `from`/`to`, nomor halaman, jumlah run, selesai/parsial/gagal, fallback, p95, tren harian, dan jumlah keputusan kebijakan. Dashboard menampilkan **maksimal 1.000 run per halaman** dalam jendela 30 hari; angka tiap halaman **bukan total 30 hari**. Gunakan tombol halaman lebih lama untuk meninjau halaman lain. Jangan merata-ratakan p95 halaman untuk mengklaim p95 seluruh periode. Jika dashboard tidak tersedia, catat “tidak dapat dinilai”, bukan nol.
- Jalankan **hanya di lingkungan yang memang hendak dinilai**, oleh operator berwenang: `pnpm --filter @workspace/scripts run gate:agent-quality` (implementasi `scripts/src/agent-quality-gate.ts`). Perintah ini membaca ledger pada database lingkungan itu dan mencetak agregat; kode keluar **0 = PASS**, **2 = NOT_READY**, **1 = FAIL atau kesalahan eksekusi** (bedakan status keluaran dari pesan error). Jangan mengarahkan perintah ke database lain atau menyebut hasil development/test sebagai bukti produksi. Bila perlu pemrosesan mesin, `pnpm --filter @workspace/scripts run gate:agent-quality -- --format=json`; **jangan menempelkan JSON utuh ke tiket**.
- Gate kanonis: run terminal `COMPLETED`, `FAILED`, `PARTIAL` untuk `trainer-intelligence` yang **dibuat** dalam 30 hari terakhir. Syarat sampel produksi sedikitnya **100 run** dan rentang pengamatan dari run pertama ke terakhir sedikitnya **14 hari**. Batasnya completed **≥95%**, failed **≤1%**, fallback **≤5%**, p95 latensi terminal **≤15.000 ms**. Rate adalah bagian dari run terminal; `PARTIAL` masuk penyebut tetapi bukan completed atau failed. p95 memakai run terminal dengan waktu mulai/selesai valid. Status `NOT_READY` dapat menyertakan alasan metrik; itu **bukan** izin melanjutkan rollout. `PASS` hanya gate metrik, **bukan** persetujuan baseline operasional.
- Jangan membandingkan angka mentah dashboard dengan gate: dashboard mencakup semua agent, juga run non-terminal, dan hanya satu halaman; gate mencakup seluruh run terminal agent tertentu di jendela waktunya sendiri. Bandingkan tren yang sepadan (UTC, jendela, populasi, status, waktu pengambilan), dan tandai batas cakupan. Dimensi versi/provider/model pada tampilan bukan izin untuk menyalin metadata bebas dari ledger.

**Yang boleh dicatat di tiket/rapat:** tanggal/waktu UTC, lingkungan, versi kebijakan gate, status PASS/NOT_READY/FAIL, alasan metrik dalam bentuk angka, ukuran sampel, jumlah hari pengamatan, rate, p95, jumlah per halaman, nomor halaman, tren harian agregat, keputusan eskalasi, penanggung jawab, dan hasil pemeriksaan regresi lulus/gagal. Hindari menyalin potongan log atau respons mentah; tulis ulang hanya angka dan kategori yang diizinkan.

**Dilarang disalin, diekspor, difoto untuk tiket, atau dikirim ke vendor/chat:** nama/email/ID learner atau trainer, ID run/record/evidence, cursor, prompt atau payload provider, `objective`, `toolRefs`, `evidenceRefs`, `resultSummary` utuh, isi bukti, review/diagnostic, respons agent individual, hash/JSON ledger, bearer token, maupun baris database individual. Jangan jalankan `SELECT *` terhadap ledger atau tabel learner sebagai langkah diagnosis. Jika agregat belum cukup, minta engineering menambah instrumentasi agregat yang aman dan tinjauan governance; jangan memperluas akses data untuk memenuhi tiket.

## Pemeriksaan harian (awal giliran dan setelah rilis)

1. Buka panel admin; periksa ketersediaan, waktu dan nomor halaman, status counts, policy counts, fallback rate, p95, dan tren UTC. Jika ada halaman lama, telusuri untuk melihat pola; tulis angka **per halaman** dengan penyebutnya. Jika `DENY`/status tidak dikenal melonjak, jangan tafsirkan sebagai kesalahan learner.
2. Jalankan gate pada lingkungan yang benar. Catat status, alasan, sampel, periode observasi, rates dan p95 tanpa menyimpan keluaran mentah. Cocokkan arah tren, bukan angka dashboard vs gate secara langsung.
3. Tandai **P0** segera bila ada indikasi kebocoran identitas/prompt/isi bukti, akses tak berwenang, perubahan/hapus ledger, perubahan domain oleh agent, atau dugaan integritas ledger yang terkonfirmasi dengan pembandingan agregat setara. Hentikan rollout/ekspansi agent dan eskalasi segera ke engineering keamanan + governance. Jangan teruskan artefak sensitif sebagai bukti.
4. Tandai **P1** bila gate `FAIL` karena failed >1%, fallback >5%, completed <95%, p95 >15 detik; juga bila panel/gate tidak dapat dinilai atau terjadi lonjakan parsial/gagal yang belum dapat dijelaskan. Tahan rollout, kirim ke on-call dan governance pada hari yang sama; periksa lagi setelah mitigasi. Jika gate `NOT_READY` (lingkungan bukan produksi, sampel/hari kurang, atau p95 tak tersedia), tahan deklarasi baseline dan perluasan kapabilitas; dokumentasikan alasan, bukan anggap PASS.
5. Catat tindakan, pemilik, waktu pemeriksaan ulang, dan keputusan governance. Jangan mengubah data ledger atau domain untuk “memperbaiki” angka.

## Investigasi tanpa record individual

| Sinyal | Pemeriksaan aman | Langkah dan keputusan |
| --- | --- | --- |
| Fallback/`PARTIAL` naik | Cek jumlah dan penyebut per halaman, tren UTC, rate gate, distribusi versi/provider/model yang sudah ditampilkan sebagai agregat. `trainer-intelligence` memakai fallback deterministik saat pemilihan provider gagal/invalid (`artifacts/api-server/src/lib/trainer-intelligence.ts`). | Engineering cek kesehatan/latensi provider dan perubahan versi atau konfigurasi dari metrik teragregasi; jangan buka permintaan/respons provider. Jika >5% di gate, P1 dan hentikan rollout; jika ada indikasi payload privat terkirim, P0. |
| Failed rate/completed turun | Periksa terminal gate (bukan semua status dashboard), tanggal jendela dan jumlah sampel; lihat tren jumlah gagal dan keputusan kebijakan per halaman. | Cek ketersediaan layanan dan kegagalan penyimpanan melalui kategori error yang disanitasi; jangan tempel stack trace yang mungkin memuat payload. Jika failed >1% atau completed <95%, P1; kegagalan pencatatan ledger yang terbukti adalah P0. |
| Ledger mismatch | Pertama cocokkan populasi, waktu `from`/`to`, zona UTC, status terminal, agent, dan pagination. Di **satu halaman yang sama**, `runCount` harus sama dengan jumlah `statusCounts` dan dengan jumlah `trends.runCount`; jumlah completed/partial/failed harus sesuai status counts halaman. Jangan bandingkan rate halaman dengan gate tanpa cakupan setara. | Jika kesalahan hanya beda cakupan/jendela, tulis penjelasannya. Jika invariant halaman gagal atau agregat setara tetap tidak cocok pada snapshot yang stabil, tandai “dugaan mismatch” dan eskalasi engineering; verifikasi ulang lewat agregasi read-only yang hanya menghasilkan count (tanpa ID/baris). Jika integritas ledger atau proteksi append-only terbukti rusak, P0, stop rollout; jangan edit/hapus/backfill secara ad hoc. |
| p95 naik/tidak tersedia | Bandingkan p95 gate dengan 15.000 ms dan p95 halaman dengan tren status pada halaman yang sama; p95 gate hanya latensi terminal valid, bukan waktu respons UI atau rata-rata halaman. | Engineering cek metrik durasi dependency/provider dan database secara agregat. Jika gate >15 detik, P1; jika `null`, catat `NOT_READY`/keterbatasan observasi dan tahan baseline. Jangan menyimpulkan p95 30 hari dari p95 halaman. |

## Pemeriksaan mingguan dan sebelum membuka rollout

1. Tinjau 30 hari dengan gate produksi dan dashboard per halaman; dokumentasikan volume, sebaran hari, perubahan versi/provider/model teragregasi, kasus P0/P1, mitigasi dan pemilik. Jangan ratakan rates antarhalaman tanpa pembobotan dan jangan gabungkan p95 antarhalaman. Kenaikan volume saja bukan bukti kualitas.
2. Verifikasi **structural gates** lewat regresi pada lingkungan uji **terisolasi** (jangan menjalankan fixture pada produksi). Dari root proyek:
   - `pnpm --filter @workspace/api-server run test:agentic-contracts` — kebijakan READ/PROPOSE tanpa eksekusi, seleksi kode fakta tervalidasi, fallback saat respons tak sah.
   - `pnpm --filter @workspace/api-server run test:agentic-integration` — otorisasi anonymous/role salah dan batas antar-trainer; payload provider hanya kode/agregat (privacy); checksum/count tabel domain sebelum/sesudah run tidak berubah (**domain non-mutation**); UPDATE/DELETE ledger ditolak (**append-only protection**).
   - `pnpm --filter @workspace/api-server run test:agent-observability` — admin-only, respons agregat tidak mengandung penanda privat, pagination dan agregasi aman. Perintah integrasi memakai skema uji sementara dan memerlukan database uji yang sudah disiapkan; jangan mengganti target dengan produksi.
   - `pnpm --filter @workspace/scripts run test:agent-quality-gate` — kebijakan numerik gate. Hasil test adalah bukti regresi, bukan pengganti inspeksi produksi atau audit keamanan.
3. Untuk tiap gate struktural tulis **PASS/FAIL/tidak diperiksa**, waktu, lingkungan uji, dan referensi hasil CI internal tanpa mengunggah stdout/log mentah. Bila tidak dapat diuji, perlakukan sebagai **belum terverifikasi**, bukan lulus. Perubahan perilaku agent, provider, akses, atau ledger menuntut pengulangan gate terkait sebelum rollout.
4. Governance boleh menyatakan **Verified Operational Baseline** hanya setelah gate metrik produksi `PASS`, keempat gate struktural (privacy, authorization, append-only, domain non-mutation) punya bukti regresi terkini yang lulus, dan insiden P0/P1 terbuka telah ditangani. `PASS` metrik saja tidak cukup; jangan menambah agent/kapabilitas sampai governance menyetujui.

**Kriteria membuka kembali rollout:** engineering menjelaskan akar masalah dalam kategori agregat, mitigasi telah diterapkan tanpa mengubah histori ledger, tren pascaperbaikan terpantau, gate kembali memenuhi syarat produksi, pemeriksaan struktural relevan lulus, lalu governance mencatat keputusan eksplisit. Jika data belum cukup atau kontrol privasi belum dapat diverifikasi, tetap tahan rollout dan eskalasi; jangan menurunkan ambang batas setelah melihat hasil.
